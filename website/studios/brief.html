Micro levels: hundreds of millions of polygons

  • A micro level stores one 16-bit height per grid point on each triangle of the highest subdivision level, and the micro triangles are worked out on the fly. Micro levels 3 to 7 give 64 to 16,384 micro triangles per base triangle, at 1.4 to 1.05 bytes per micro triangle. Measured: the 201-million-micro-triangle scene peaks at 1.2 GB of RAM for the whole application (first table).
  • A micro level larger than the resident cache the hardware profile allows (a quarter of the memory when there is no profile yet) is kept out of core in a file in the cache folder; only the parts being sculpted or viewed stay in memory.
  • The view lowers the detail of far and small areas until a frame fits a budget: 2 million triangles on the laptop profile, 8 million on the workstation profile.
  • Without micro levels, subdivision levels cost about 90 bytes per triangle, which is why a 300-million-triangle mesh would need 27 GB that way. (Arithmetic from the data layout; the measured case is the 104M-triangle sphere in the first table, which peaks at 14.4 GB.)

Source: Micro levels and Very large levels and laptops; the per-micro-triangle bytes and the detail budgets are properties of the format, not run results. Brushes that work on micro levels, and those that do not, are listed on that page.

Run it yourself

sculptforge --benchmark standard-15m      # built-in 15M-triangle head, identical on every computer
sculptforge --benchmark standard-33m      # the 33M head
sculptforge --benchmark core-100m         # 104M micro triangles (core-200m: 201M)
sculptforge --benchmark --benchmark-sizes 100   # a 104M-triangle subdivided sphere
sculptforge --bench                       # per-brush and view costs, see docs/performance.md

The scene, strokes (scripted pen, 240 pointer samples a second, Clay at 25, 60 and 120 px, Move, Smooth, a 240 px Clay, then an orbit) and the meaning of frame p50, p95, p99, lag and worst stall are described on Benchmarks. The results table on that page lists the runs above, one row each.

Where it is still slow

  • Big brushes (120 and 240 px) on very dense meshes trail the pen on every machine tested, the RTX 3060 desktop included: the stroke lands, but late.
  • Orbiting 104 million real triangles right after a stroke has one slow frame on the RTX 3060 (about 348 ms, first table), although the average is far above 30 frames a second.

Sources: the first table above and How fast?, What's still slow. No real integrated-graphics laptop is in the measured set yet; that tier is simulated and each result says so.

3. Linux desktop

One build, native on both display servers.

  • Every Linux package (.deb, .rpm, AppImage, Flatpak, tar.gz) opens as a native Wayland window on a Wayland desktop, without XWayland, and as a normal X11 window on an X11 session. SDL_VIDEO_DRIVER=x11 forces X11.
  • On Wayland the window stays sharp at fractional and HiDPI scales (125%, 150%, 200%). Title bars come from the desktop, or from libdecor on GNOME.
  • Pen tablets work on both. On Wayland, pressure, tilt, the eraser end and side buttons come through the desktop's tablet protocol (tablet-v2), so the tablet is set up in the desktop's settings, not with X11 tools such as xsetwacom.
  • Edit > Preferences > Tablet > Troubleshooting details shows the SDL version, the video driver in use (wayland or x11) and what the pen sends, with a Copy button for bug reports.
  • CI builds SDL with Wayland and X11 on Ubuntu 22.04 (Wayland 1.20, the oldest headers the packages build against) on every code change, and fails if the Wayland backend is not built.

Sources: Install guide, Wayland and X11; Troubleshooting; job oldest-linux in ci.yml. Pen pressure on Wayland and X11 was fixed in 0.12.0 (CHANGELOG.md, "Pen pressure on Wayland and X11").

Formats, LODs, UVs, textures

  • Formats: OpenUSD (.usda, .usdz), FBX (reads any version, writes 7.4 binary), glTF/GLB, OBJ, PLY, STL (binary and ASCII read, binary write), Bridge files and the project format .sfproj, which is a documented ZIP of JSON and binary arrays (docs/project-format.md).
  • Units: glTF, USD and OBJ are written Y-up, 1 unit = 1 metre. FBX is written in centimetres. STL is written in millimetres, Z up.
  • LOD chains: quadric decimation, 2 to 6 levels, reduction 0.1 to 0.9 per level, blend shapes kept on every level; exported as one .glb per level, as an FBX LOD group, or sent to Unreal. Headless: export_lods path=out/rock.glb levels=4 ratio=0.5.
  • UVs and UDIM: a UV Editor shows the layout over the UDIM tiles. Bakes write one file per UDIM tile with udim=true. Painting goes into one texture per Part; UVs outside the 0 to 1 square are not painted yet.
  • Bakes: normal, object_normal, displacement, ao, cavity, color, curvature, thickness, position, id, from a Part, all Parts, a subdivision level or a micro level, 512 to 8192 pixels.
  • PBR: PBR channel painting with the painted texture carried into GLB, USDZ and OBJ (.mtl) exports.

Sources: Formats table, Exporting, Baking (UDIM tiles), UV Editor, PBR painting. Exports are checked with other tools than our own loaders by a script in the repository, tools/export_check/run.sh: the Khronos glTF validator, OpenUSD's validation framework, and ufbx in strict mode. That script is run by hand, not by the CI workflows.

6. Automation

The same commands run in the app, the command line, Python and an MCP server.

  • Command line: sculptforge-cli runs every editing operation without a display: imports, remeshing, decimation, LOD chains, FBX, USD and glTF export, splat conversion and AI generation. sculptforge-cli --list lists every pipeline command. sculptforge --render out.png --turntable 8 renders review images and turntables offscreen; it needs an OpenGL 3.3 context, so on a headless Linux node run it under Xvfb.
  • Python: import sculptforge gives the same commands plus NumPy access to the mesh (doc.vertices, doc.triangles). The Reference Platform builds are built and tested against Python 3.13.
  • Rez: see Platforms. SCULPTFORGE_BRUSH_PATH and SCULPTFORGE_STUDIO_BRUSHES point the app, CLI and module at read-only studio brush shares; SculptForge never writes into them.
  • MCP, for AI agents: sculptforge-cli --mcp serves the Model Context Protocol over standard input and output only, with a scene of its own and no window; the AI tool starts it as a child process and nothing listens on a port. sculptforge-cli --mcp --attach lets an AI tool work in an open SculptForge window; it is off by default and the policy file can forbid it. The guide gives the setup for Claude Code, Claude Desktop, Cursor, Codex CLI and Antigravity CLI. Each command is checked against the policy's categories and written to the audit log.
  • ComfyUI, a separate feature: Generate 3D can use "ComfyUI - your server" to run image or text to 3D on your own computer or a studio GPU server. The bundled text-to-3d workflow uses FLUX.1 schnell and Hunyuan3D 2.1, and any other ComfyUI workflow can be chosen. ComfyUI listens on 127.0.0.1:8188 by default; for another computer start it with --listen, only on a network you trust, because ComfyUI has no login. This is not related to the MCP server.
  • AI is on by default and can be turned off: Edit > Preferences > AI, SF_AI=off or --no-ai (every AI feature off and locked, in the app, CLI, MCP and Python), or ai.enabled: false in the policy file. With AI off the MCP server stays; the AI commands leave its tool list.
sculptforge-cli --set in=/ingest/scan_042.ply --set usd=/assets/scan_042.usda --set glb=/assets/scan_042.glb -c '
  open path=$in
  splat_transform rotate_x=180 fit=true
  splat_clean
  splat_to_mesh detail=320 preset=game color=texture
  export_usd path=$usd
  export_lods path=$glb levels=4 ratio=0.5
'

Sources: Scripting and automation (MCP), Headless and farm use (the example above is from it), Image and text to 3D, What leaves your computer, Environment variables.

8. How it is built

  • Release cadence: 28 releases in the past 30 days, from 2026-11-04 (0.11.0) to 2026-11-11 (0.12.10). Every release has an entry in the public CHANGELOG.md and notes on the releases page. Counted from the non-pre-release GitHub releases and from the changelog's version headings; both give 28.
  • Public queue and vote: every feature idea is in the public feature queue, with its state; members vote on what is built next (vote). Bug fixes and security fixes go out to everyone the same day.
  • On every push to main and on every pull request (ci.yml): build and test on Linux x86_64 and Linux ARM64 (Ubuntu 24.04), macOS (macOS 15) and Windows (Windows Server 2022 runner), each with the full test suite split in parallel shards; the oldest-Linux-headers build (Ubuntu 22.04); and a trademark check of the text and the images. Changes that touch only the website skip the build and test jobs.
  • On main, in each merge batch before it reaches main, and on request: the VFX Reference Platform builds in Rocky Linux 8 and 9 containers with GCC 14, the Python 3.13 module tests and the glibc check, and the Blender add-on tests (bpy 4.2.0, 5.2.3, 5.3.0). Other branch runs skip these unless labelled.
  • Every day: a scheduled workflow runs the tests labelled nightly (stress and benchmark checks) on Linux x86_64 (nightly.yml).
  • Android: a workflow builds the APK on every push that changes the Android side (android.yml).
  • Source: GPL-3.0-or-later, public on GitHub; docs/testing-flow.md describes the test tiers.

9. What it does not do yet

Known gaps, as of 2026-11-12

  • OpenUSD: binary .usdc files and references or payloads are not read. Layers, variants and references are not authored.
  • Alembic: no export, and no import.
  • OpenColorIO: no OCIO viewport display.
  • Signing: Windows builds are not Authenticode-signed; the macOS app is not notarized.
  • Unreal: the link has been tested against a stand-in editor that speaks the same protocol, not against every Unreal version. Layered sculpts reach Unreal as skeletal meshes without the LOD chain.
  • Android: an early test build with the desktop layout; no tablet layout of its own yet; not in a stable release.
  • Packages: winget is in review, AUR is not published, the apt and dnf repositories are not live.
  • Textures: painting goes into one texture per Part; UVs outside the 0 to 1 square (other UDIM tiles) are not painted. UDIM tiles do bake.
  • Micro levels: a micro level moves the surface in and out, never sideways. Tendril, Nudge, VDM stamps and custom recipe brushes do not apply to it, and Vertex Paint, sculpt layers, face group colours and the wireframe are not shown on micro levels yet.
  • Performance: big brushes (120 and 240 px) on very dense meshes trail the pen on every machine tested; the slowest frame of a 104M-triangle orbit right after a stroke is about 348 ms on the RTX 3060; no real integrated-graphics laptop is in the measured set; the public benchmark results table has no submitted results yet.
  • Maya: the shelf is an early release.
  • Silent install: switches for the Windows installer are not documented.
